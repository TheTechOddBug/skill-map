## Decision log

> Canonical index of every locked-in decision. Each row carries a stable number so the rest of the repo, `spec/`, `AGENTS.md`, commits, PR descriptions, changesets, can cite a single anchor (e.g. *"per Decision #74d"*) instead of paraphrasing the rationale.

Conventions:

- **Numbering is sparse on purpose**. Sub-items (`74a`…`74e`) land where they belong thematically rather than at the end of the list; gaps are reserved for future rows on the same topic.
- **Thematic groups, not chronology**. Rows are grouped by domain (Architecture, Persistence, Jobs, Plugins, UI, etc.). Reading a single group gives you every decision on that surface.
- **Most entries have a narrative counterpart** elsewhere in `ROADMAP.md` or in `spec/`, the table row is the one-liner, the narrative section is the rationale. If an entry is table-only, its row states the "why" in full.
- **Source of truth for AI agents**. `ROADMAP.md` is above `AGENTS.md` in the project authority order, and this Decision log is where every agent should look up locked-in rationale. `AGENTS.md` carries only operational rules (persona activation, agent workflow, spec-editing checklist); it does **not** duplicate the decision table. Citations from `AGENTS.md`, commits, PRs, or changesets that reference a decision MUST use the `#N` anchor here (e.g. *"per Decision #74d"*) rather than paraphrasing. The spec still wins over both.
- **Immutability, with one narrow exception**. Rows are not edited away once locked, a changed decision gets a new row and the old row flips to "superseded by #N" with a date. That keeps history auditable instead of rewriting it. **Exception**: a row MAY be deleted if it was **born redundant** (never stated anything the surrounding rows did not already say; duplicated from the outset rather than revised). The deletion note goes in the changeset or commit that removes the row. Numbering stays sparse by design (§Conventions), so a gap is acceptable. This exception does NOT apply to a row that was once canonical and later superseded, that still uses the supersede-by-new-row path.

| 148 | **Untrusted YAML parses only through the bounded entry point** | Locked 2026-07-28 (cli-hacker audit H2). Every YAML skill-map reads is attacker-authored under clone-and-scan (`.md` frontmatter, `.sm` sidecars), so `js-yaml`'s trusted-input defaults are a footgun and calling `load()` directly is banned: all four call sites (frontmatter parser, orchestrator frontmatter, sidecar parse + store) go through `kernel/util/safe-yaml.ts`, and a new one is a review defect. The helper pins `JSON_SCHEMA` (no `!!js/*` tag can construct executable values, carrying audit L3 forward) and bounds expansion. **The subtle part, which cost a wrong first fix**: `maxAliases` bounds alias TOKENS, not the graph they denote, and two references per level buy `2^(N/2)` leaves, so no value of it closes the hole. A ~400-byte document with 81 tokens still denoted 9^9 nodes; `load()` returned a cheap shared-reference DAG and the heap died downstream where it got materialised (`stripPrototypePollution` deep-clones, persistence `JSON.stringify`s), taking the whole `sm serve` process with it. The real bound measures the PARSED graph against a 100k-node budget with memoised subtree sizes plus cycle rejection, so the check costs distinct nodes rather than the expansion it protects against (3.6 ms for the 9^9 case). A breach throws `YAMLException`, so call sites surface it through their existing parse-error path (an issue on the node) instead of crashing. Regression coverage: `kernel/util/__tests__/safe-yaml.spec.ts`, whose load-bearing case is deliberately UNDER the token cap. |
| 150 | **Machine-local authorization lives in the scope lock, anchored to filesystem identity** | Locked 2026-07-28, closing audit C1 (Critical, RCE) and H1. Two controls stored their state inside the directory the threat model calls hostile: plugin import trust (`config_plugins`) and the privileged `PROJECT_LOCAL_ONLY_KEYS` in `settings.local.json`. Both leaned on "the file is gitignored so it cannot arrive in a clone", which describes the DEFAULT BEHAVIOUR and is not a boundary: the ignore list is the repo author's to edit and `git add -f` ships anything. A hostile repo could therefore hand a victim a pre-granted plugin (verified with a working PoC: arbitrary code executed on the first `sm scan`) or a pre-enabled `scan.followExternalSymlinks`. **Resolution**: a third storage category, machine-local authorization, in `.skill-map/scope.lock.json`. Each record carries a grant derived from the `.skill-map/` directory's `ino` + `birthtimeNs`, which git does not transport, so a record made elsewhere cannot verify here regardless of how it arrived. The user REJECTED moving the store or a key to `$HOME`, and the trade-off is stated plainly rather than papered over: this is unpredictability, not secrecy, and it is not authentication (local read implies a forgeable grant, which is fine since local read implies local write implies editing the plugin directly). **Three properties are load-bearing and each was learned by having the alternative break.** (a) Grants are per SUBJECT, never per store: a store-wide stamp is refreshed by any legitimate write and thereby blesses every unrelated record beside it, so cloning a repo carrying `evil`, letting the first scan correctly ignore it, then running `sm plugins trust legit` would have executed it. It also means `writeConfigValue`'s whole-file read-modify-write needs no defending, it copies an attacker's key back to disk and that key still never verifies. (b) `dev` is NOT compared (an anonymous bdev reassigned at mount time, so it reshuffles on every container/WSL restart and would revoke grants on a routine restart, training exactly the reflexive re-granting the gate cannot survive) and `birthtimeNs === 0` means UNUSABLE, never an `ino`-only fallback (birth time is identically zero on 9p/`/mnt/c`, `/proc` and `/sys`, where inode numbers are structured and consecutive, so the fallback would be weakest exactly where it engaged and selectable on demand via a committed `.skill-map -> /proc` symlink). (c) `absent` denies: pre-mechanism state and an omitted grant are the same shape from inside, so grandfathering would be a one-line bypass; the cost is that existing operators re-grant once. Trust also LEFT the database, which deletes and rebuilds itself on schema drift (roughly every pre-1.0 minor), a wrong home for a vetting decision. Mismatch is ambiguous by construction (copied, restored, moved, re-cloned, or hostile, indistinguishable from inside), so messages state the fact and never accuse, there is no bulk re-adopt (it would turn the exploit into social engineering), and `sm plugins trust --all` now lists the ids and confirms. Normative: `spec/architecture.md` §Storage rule + §Config layering, `spec/db-schema.md` §`config_plugins` (REMOVED), `spec/cli-contract.md` §Plugins + §sm doctor. |
| 151 | **"Click the whole row" is for BOOLEAN rows only** | Locked 2026-07-28 while extending the Plugins list's row-click affordance to the rest of Settings (`[smToggleRow]`). A wide row (label plus a paragraph of description on the left, a small switch pinned right) makes the switch the fiddliest target on screen, so the whole row flips it. The rule is the SCOPE: only a row whose single control is a boolean gets the gesture. Rows fronting a select, a text field, a path list or an install button keep requiring their control, because "click anywhere" is only unambiguous when there is one thing the click could mean; on a multi-option row it would have to pick a value arbitrarily, and on an action row it would fire a side effect from an idle gesture. Two implementation consequences follow from the same rule and are the reason it is written down. **The affordance is keyed on the directive, not on the row class**: `.settings-project__row` is also worn by the hook / skill / reference-paths rows, so both the click handler and the `cursor: pointer` hang off the `[smToggleRow]` attribute selector, which cannot drift away from the behaviour the way a shared class does (a `:has()` rule also drops the hand cursor when the row's switch is disabled). **The gesture is forwarded to the control, not to the component**: the directive dispatches the click on `<p-toggleswitch>` rather than calling each host's toggle method, so it needs to know nothing about per-row signals, pending-key bookkeeping or confirm dialogs, and it inherits PrimeNG's own disabled / readonly guard instead of re-deriving it. It deliberately adds NO `role` and NO `tabindex`: a container pretending to be a button is exactly what erased row contents from the accessibility tree in the same day's audit (see the A11y pass entry in `ROADMAP.md`), so this stays a pointer convenience and the switch remains the focusable control. |

| 149 | **Every file skill-map creates is owner-only (`0o600`)** | Locked 2026-07-28 (cli-hacker audit S2). The settings files and `.sm` sidecars were already created owner-only, because `writeFileAtomicExclusive` sets the mode at `open()` time, but the project DB and its backups landed `0o644`, world-readable under the common `022` umask, while carrying the same scanned content (rendered job contents embed node bodies). The split was accidental, not a decision: `DatabaseSync` and `copyFileSync` take no mode argument, so those two paths silently inherited the umask. The rule is now uniform, and the mechanism is the shared best-effort `chmodOwnerOnlyBestEffort` in `kernel/util/atomic-write.ts`, applied after DB create, after a backup copy, and after a restore. Best-effort by contract: Windows and non-POSIX filesystems reject `chmod`, and tightening permissions is hardening, never a correctness gate, so a failure must not fail the operation that produced the file. A new artifact that can contain scanned content adopts this by default; writing one that does not is the thing to justify. Regression coverage: `kernel/adapters/sqlite/__tests__/db-file-mode.spec.ts`. |

| 147 | **CLI output sanitization: payload channels are exempt, human views are not** | Locked 2026-07-28 while closing a cli-ruler finding that the jobs / record / sidecar / bump / migrate verbs emitted DB- and model-authored strings unsanitized. **Fixer queue hygiene (landed 2026-07-16, supersede):** two fixer jobs for the same `(node, fixer)` could sit queued at once, because the duplicate index keys on `content_hash` and a sibling fixer's edit changes the body, so the second submit was technically a different job. Resolution (user decision 2026-07-16, "reemplaza"): a fixer submit that finds an ACTIVE queued sibling for the same `(extension, node)` with a DIFFERENT `contentHash` CANCELS it and enqueues the new job in one transaction, reporting the superseded id on stderr. ### Step 15, Distribution polish

- **Single npm package**: `@skill-map/cli` ships CLI + UI built (`ui/dist/` copied into the package at publish time). Two `bin` entries, `sm` (short, daily use) and `skill-map` (full name, scripting). Same binary, two aliases. Single version applies to both surfaces; CLI ↔ UI key mismatches degrade gracefully (unknown keys are warned + ignored, never fatal). Versioning details in §Stack conventions.
- **Alias / squat-defense packages** (historical): an `alias/*` glob workspace published two un-scoped placeholders to lock names against third-party squatters: `skill-map` (un-scoped top-level) and `skill-mapper` (lookalike). Each shipped a single `bin` that printed a warning to stderr pointing at `@skill-map/cli` and exited with code 1. They never delegated, never wrapped the real CLI as a dependency, never installed side-effect-free. Once both names were locked at `0.0.2` and a `npm deprecate` notice was attached on each (the official npm-side equivalent of the same redirect message, surfaced at install time and on every `npm view`), the workspaces themselves were dropped from the tree. The `@skill-map/*` scope is already protected by org ownership (the moment `@skill-map/spec` was published).

  Two extra names attempted at first publish that never made it into `alias/*`:

  - **`skillmap`**, npm's anti-squat policy auto-blocks "names too similar to an existing package" once `skill-map` is published. Got E403 with `"Package name too similar to existing package skill-map"`. Net effect: no third party can publish `skillmap` either, so the name is de-facto reserved. Cheaper than maintaining a workspace.
  - **`sm-cli`**, already taken on npm at first-publish time by an unrelated project. Not critical: `sm` is the binary name (alias of `skill-map`), not a package name we ship. The binary is delivered exclusively through `@skill-map/cli`, so a third party owning the `sm-cli` name does not affect the skill-map ecosystem.

  Lesson for future placeholder additions: `npm view <name>` before creating the workspace to detect both occupied names and likely anti-squat collisions; only commit a workspace if the name is publishable. And: a workspace is only worth keeping while you might re-publish it. Once the redirect lives in `npm deprecate`, the local workspace is dead weight, drop it.

#### Distribution flow (end-to-end)

How a single package travels from this repo to a consumer's project:

```
   ┌────────────────────────────────────┐
   │   skill-map repo (this monorepo)   │
   │   ─────────────────────────────    │
   │   spec/         → @skill-map/spec  │
   │   src/          → @skill-map/cli   │
   │   ui/           → built and copied │
   │                   into src/dist/ui │
   │                   at publish time  │
   │   alias/<name>/ → name placeholders│
   │                   (skill-map, etc.)│
   │                                    │
   │   Versioned by changesets;         │
   │   integrity hashes enforced.       │
   └─────────────────┬──────────────────┘
                     │  release workflow
                     │  (Version Packages PR → merge)
                     │  changeset publish
                     ▼
   ┌────────────────────────────────────┐
   │   npm registry                     │
   │   ─────────────────────────────    │
   │   @skill-map/spec  (schemas+types) │
   │   @skill-map/cli   (CLI + UI dist) │
   │   skill-map        (deprecated)    │
   │   skill-mapper     (deprecated)    │
   └─────────────────┬──────────────────┘
                     │  npm i -g @skill-map/cli
                     │  (or `npx @skill-map/cli …`)
                     ▼
   ┌────────────────────────────────────┐
   │   consumer machine                 │
   │   ─────────────────────────────    │
   │   $PATH: sm, skill-map             │
   │   node_modules/@skill-map/cli/     │
   │   ├── dist/         CLI bundle     │
   │   └── ui/           UI bundle      │
   │                                    │
   │   .skill-map/                      │  ← user-supplied
   │   ├── settings.json       optional │
   │   ├── settings.local.json optional │
   │   └── plugins/<id>/       drop-in  │
   └─────────────────┬──────────────────┘
                     │  sm ui [--port N] [--config path]
                     │  (also: sm scan, sm check, …)
                     ▼
   ┌────────────────────────────────────┐
   │   sm ui process                    │
   │   ─────────────────────────────    │
   │   loadSettings() walks the         │
   │   hierarchy, deep-merges, validates│
   │                                    │
   │   static HTTP server on            │
   │   localhost:<port> :               │
   │     GET /              → ui/*.html │
   │     GET /assets/*      → ui/assets │
   │     GET /config.json   → merged    │
   │                          settings  │
   └─────────────────┬──────────────────┘
                     │  browser open
                     ▼
   ┌────────────────────────────────────┐
   │   Angular bundle (in browser)      │
   │   ─────────────────────────────    │
   │   APP_INITIALIZER fetch /config    │
   │   merge over compile-time defaults │
   │   render graph + filters + HUD     │
   │                                    │
   │   No build tooling at runtime.     │
   │   No file system reads.            │
   └────────────────────────────────────┘
```

The UI bundle is **agnostic to who serves it**, Step 15 ships `sm ui` as the canonical server, but a third-party host (nginx, S3, Caddy) that places a `config.json` next to `index.html` works identically. Same HTTP contract, zero coupling between the UI and the CLI runtime.
