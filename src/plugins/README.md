# Built-in extensions (built-in plugins)

The reference implementation's bundled extensions live here, organized by extension kind. Each is a directory with a manifest + implementation + a sibling `*.test.ts` (the kernel treats a missing test as a contract-check failure for built-ins).

The built-in **plugins** are declared in [`built-ins.ts`](./built-ins.ts):

- **`claude`** / **`antigravity`** / **`codex`** / **`agent-skills`** group the vendor Provider extensions (and, for `claude`, the two vendor-specific extractors that decode its `@`-directive and `/`-slash grammar). Today `antigravity`, `codex`, and `agent-skills` each ship just their Provider; `claude` ships its Provider plus the two extractors.
- **`core`** ships the kernel-internal primitives (every Rule, the Formatter, the markdown / URL-counter Extractors, the `core-markdown` fallback Provider).

Every extension is independently toggle-able by its qualified id `<plugin>/<ext-id>`, satisfying §Boot invariant: "no extension is privileged". Plugins are presentational grouping only; the bare plugin id maps to a CLI / BFF cascade macro (`sm plugins disable claude` fans out across every extension inside `claude`; multi-extension plugins need `--yes` in non-TTY contexts).

## Naming convention: AI (probabilistic) extensions

Probabilistic (AI, `mode: 'probabilistic'`) built-ins follow the pattern **`ai-<subject>-<kind>`**: a finder Analyzer ends in `-analyzer` (`ai-redundancy-analyzer`, `ai-contradiction-analyzer`, `ai-incoherence-analyzer`), a fixer or summarizer Action ends in `-action` (`ai-summarizer-action`, `ai-redundancy-action`, `ai-contradiction-action`, `ai-incoherence-action`). The `ai-` prefix marks the AI family at a glance and the `-<kind>` suffix names the extension kind in the id itself; the UI derives a bare label by stripping both (`ai-redundancy-analyzer` reads as `redundancy` on a button). **A fixer is named after the finder it serves**, so `ai-<subject>-action` pairs with `ai-<subject>-analyzer` (`ai-redundancy-action` fixes `ai-redundancy-analyzer`, `ai-contradiction-action` fixes `ai-contradiction-analyzer`, `ai-incoherence-action` fixes `ai-incoherence-analyzer`); the pair collapses to one subject label on the inspector's two-state Detect/Fix button. A probabilistic Action without `precondition.analyzerIds` (the summarizer, `ai-summarizer-action`) is not a fixer, so it names its own subject. A fixer for a DETERMINISTIC analyzer (`ai-reference-action`, which fixes `core/reference-broken`) is EXEMPT from the pairing convention: it consumes a deterministic Rule, not an `ai-*-analyzer` partner, so it is named after what it fixes (references) and the pairing guard skips it. Deterministic built-ins keep their plain `<subject>` ids (`node-stability`, `name-collision`, `node-bump`). The pattern (and the fixer/finder pairing, with the deterministic-analyzer exemption) is enforced by guard tests in [`__tests__/built-ins-modes.spec.ts`](./__tests__/built-ins-modes.spec.ts); any new probabilistic built-in must follow it. The codegen (`scripts/generate-built-ins.js`) derives the export binding without doubling the kind suffix, so the folder `ai-redundancy-analyzer` exports `aiRedundancyAnalyzer`.

| Rule | `core` | `reference-broken` | Invocation links pointing at a target that doesn't exist? Emits an `error` Issue. |
| Rule | `core` | `link-kind-conflict` | Two Extractors emit a link for the same `(source, target)` pair with different `kind` values? Emits a `warn` Issue per pair. |

| Rule | `core` | `ai-redundancy-analyzer` | FIRST probabilistic finder (stable): judges one node for internal redundancy via the job loop (`sm jobs submit` / `sm jobs claim` / `sm record`); findings of type `redundancy` land in `state_findings`, read with `sm findings`. No `evaluate()`, never runs at scan time. |
| Rule | `core` | `ai-contradiction-analyzer` | Probabilistic finder (stable): judges one node for internal contradictions (directive pairs that cannot both be followed, or whose combination is jointly risky); findings of type `contradiction`. | Rule | `core` | `ai-incoherence-analyzer` | Probabilistic finder (stable): judges one node for internal incoherence (dangling references, drifting terminology, steps out of order); findings of type `incoherence`. Same job-loop shape as `ai-redundancy-analyzer`; finders judge independently. |
| Action | `core` | `ai-summarizer-action` | Universal summarizer (experimental, ships disabled; opt-in via `sm plugins enable core/ai-summarizer-action`). A probabilistic Action with NO `precondition`, so `sm jobs submit ai-summarizer-action --all` reaches every non-virtual node; its report `$ref`s `summaries/markdown.schema.json`, the signal that drives the `state_summaries` write-through at record time. Disabled by default (user decision 2026-07-18) until its Step 16 summary card lands. |
| Action | `core` | `ai-redundancy-action` | FIRST fixer (stable): a probabilistic Action declaring `precondition.analyzerIds: ['core/ai-redundancy-analyzer']`. | Action | `core` | `ai-contradiction-action` | Fixer (stable) for `core/ai-contradiction-analyzer`: `precondition.analyzerIds: ['core/ai-contradiction-analyzer']`. At submit the kernel injects the node's contradiction findings into a `## Findings to resolve` section, stale ones included and flagged, and refuses only when the node has none at all; the processing agent edits the file to settle the conflicting or jointly-risky directive pairs, preserving every distinct requirement. skill-map never writes the body. |
| Action | `core` | `ai-incoherence-action` | Fixer (stable) for `core/ai-incoherence-analyzer`: `precondition.analyzerIds: ['core/ai-incoherence-analyzer']`. At submit the kernel injects the node's incoherence findings into a `## Findings to resolve` section, stale ones included and flagged, and refuses only when the node has none at all; the processing agent edits the file to fix dangling references, align drifting terminology, and supply missing context, without inventing facts. skill-map never writes the body. |
| Action | `core` | `ai-reference-action` | Fixer (experimental, ships disabled) for the DETERMINISTIC `core/reference-broken` analyzer: `precondition.analyzerIds: ['core/reference-broken']`. Because the analyzer is deterministic, at submit the kernel injects the node's `reference-broken` Issues (from `scan_issues`, not `state_findings`) into a `## Issues to resolve` section and refuses when the node has none; the processing agent repoints each broken reference link at its real in-project target, and asks the operator's permission (`human-decision`) before searching outside the project. skill-map never writes the body. Named after what it fixes (references), so it is exempt from the finder/fixer pairing convention. |
| Formatter | `core` | `ascii` | Plain-text dump grouped by node kind, then links, then issues. |
| Hook | `core` | `update-check` | Subscribes to `boot`. Runs the once-per-day "update available" probe + banner that lived inline on `cli/entry.ts` before the Hook kind had concrete consumers. Cache + bail conditions are unchanged from the inline call site. |
| Hook | `core` | `auto-fix` | Experimental, ships disabled (opt-in via `sm plugins enable core/auto-fix`). Subscribes to `job.completed` filtered to `extensionKind: 'analyzer'`: when a finder finishes, it resolves the inverse of Modelo B (every loaded Action whose `precondition.analyzerIds` names that finder) and `ctx.queue`s each matching fixer for the node, chaining finder -> fixer automatically. No matching fixer, or a fixer with no findings, queues nothing. |

The `boot` and `shutdown` triggers fire from `cli/entry.ts`, not from `runScan`. Hooks that subscribe to `boot` / `shutdown` are dispatched by the entry-side dispatcher built over `builtIns().hooks`; pipeline-driven triggers (`scan.*`, `extractor.completed`, `analyzer.completed`, `action.completed`, `job.*`) flow through the orchestrator dispatcher inside `runScan`. Both dispatchers share `kernel/extensions/hook-dispatcher.ts` so the indexing / filter / error-handling semantics stay symmetric across the two entry points.

### Internal-only parsers

`parsers/{frontmatter-yaml,plain}/` ship as built-in modules but are **not** registered in any plugin and are deliberately absent from the table above, they have no `kind: 'parser'` user-facing surface. Provider manifests reference them by id (`read.parser`) and the kernel-internal registry in [`../kernel/scan/parsers/index.ts`](../kernel/scan/parsers/index.ts) is the only resolution seam (frozen at seed time, not re-exported from `src/kernel/index.ts`). They live here for layout consistency with the rest of the built-ins; user plugins cannot add parsers.

## Boot invariant

The kernel-empty-boot conformance case (`kernel-empty-boot`) asserts that with **zero registered extensions** the kernel still boots and returns an empty graph. The built-ins listed above are loaded on top of that empty boot, they are indistinguishable from drop-in plugins from the kernel's point of view. `--no-built-ins` strips them all and exercises the empty-boot path at runtime.

See [`ROADMAP.md`](../../ROADMAP.md) §Plugin system for the full kind catalog. Extension kind contracts are normative in [`spec/architecture.md`](../../spec/architecture.md); the toggle model is documented in [`spec/plugin-author-guide.md` §Toggle model](../../spec/plugin-author-guide.md#toggle-model).
